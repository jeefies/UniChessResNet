12.29 GB → 3.83 GB，把传输从 10.9 小时压到 3.5 小时。

## 开发中踩到并修掉的坑

**1. Syzygy 在兵残局里不提供梯度。**
DTZ 是「距下一次清零的步数」，只要盘上有兵，推兵随时可清零，DTZ 恒为 2 左右。
只按 DTZ 排序会让白王原地打转到和棋（KPvK 实测 300 半步收不掉）。
修法：排序键改为 `(对手WDL, 是否非清零着法, DTZ)`，保住结果的前提下优先推兵。
修完 19 半步将死。

**2. 非法局面会让 python-chess 生成「吃王」走法。**
`8/8/8/4k3/8/8/4Q3/4K3 w` 看着正常，其实黑王正被将军却轮白方走。
python-chess 于是生成 Qxe5，探到不存在的表 `KQv`（少了黑王）。
引擎侧已加 `board.is_valid()` 防线。

**3. evals 库的 cp 是白方视角。**
实测确认（黑方行棋 99.8% 升序、白方行棋 100% 降序），黑方行棋时必须取负。
符号弄反会让网络学着走最差的一手，且要等到测 Elo 才会暴露。

**4. 策略软标签要先截断再归一化。**
原先在 softmax 之后才截断到前 5 条，PV 有 6~10 条时存下的概率和小于 1。

**5. `~` 不会在 Python 字符串字面量里展开。**
传输脚本把 `~/UniChess/...` 塞进 `python -c`，远端解压全部 FileNotFoundError。
rsync 那步能成是因为 ssh 在远端 shell 里展开了 `~`。已改为开头解析成绝对路径。

**6. MCTS 会饿死低先验的着法。**
`U = c·P·√N/(1+N)`，先验低到 0.0001 时 U≈0.005，被 FPU 惩罚压死。
实测一个 P=0.0001 的**一步杀在 800 次模拟里一次都没被访问**。
修法：根节点保证每个合法着法至少访问一次，代价仅 n_legal 次模拟。

**7. MCTS 模拟次数预算没被遵守。**
命中终局节点时只累加碰撞计数、不计入预算，导致搜到杀棋后循环空转
（sims=200 时某着法访问数涨到 7661）。终局结算也是一次模拟，已计入。

**8. 数据管线的瓶颈判断要先分清 I/O 和 CPU。**
最初在全量 12.29 GB 上测整批解码，只快 1.0x，因为本机 11 GB 内存装不下、
实为磁盘随机 I/O 瓶颈。换成能驻留页缓存的子集后测得 **5.9x**（16k → 96k 样本/秒）。
GPU 机 30 GB 内存 > 12.29 GB 分片，全量落地后不会有 I/O 瓶颈。

## PGN 数据：已建好但暂不混入

`data/build_pgn.py` 产出**只带价值标签**的分片，用来补 evals 数据的短板
（evals 的 FEN 只有 4 个字段，五十步计数和重复次数恒为 0）。实测产出：

```
halfmove: 0 占 42.9%, 中位数 1, 最大 99      ← evals 恒为 0
rep:      {0: 199227, 1: 764, 2: 9}          ← evals 恒为 0
策略标签: 100% 为空（人类实走是 one-hot，混进策略头会把网络拉向人类风格）
WDL:      胜 92,900 / 和 15,572 / 负 91,528，和棋率 7.8%
```

**暂不混入 Stage 1 的原因**：PGN 的和棋率 7.8%，而 evals 折算的 WDL 在均势时
和棋概率约 50%。两者不是同一件事——前者是「业余选手实际打成什么」，
后者是「强手对弈会怎样」。混进同一个价值头，网络会学到一个既不代表强手
也不代表业余的平均值。

而它要解决的问题本身可能无关紧要：MCTS 里重复和 75 步规则是**显式判定**的，
残局有 Syzygy 兜底。所以这件事**待实测**——Stage 1 训完后对比
「推理时 halfmove/rep 置零」与「用真实值」两种配置的 Elo，没差别就不必动。

训练侧已支持：策略标签全零的样本自动屏蔽策略损失（`soft_cross_entropy` 的 mask），
不需要改 96 字节记录格式。

## MCTS 耗时构成（决定 Stage 3 的收益预期）

5070 Ti 上实测 **6,408 nodes/s**（batch 512，fp16 推理），耗时拆解：

| | 占比 |
|---|---|
| GPU 前向 | ~53% |
| CPU 局面编码 | ~12% |
| **Python 树操作** | **~35%** |

方案 Stage 3 原假设「Python 树操作是瓶颈，移植 C++ 提速 3-5 倍」。
实测树操作只占 35%，**即使移植成本降到零，上限也只有约 1.9x**。
移植仍值得做（自对弈阶段 1.9x 就是 1.9 倍学习速率），
但方案里「移植后 3-5 万盘/天」的估算需要下调。
